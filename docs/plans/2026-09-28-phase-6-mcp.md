# Phase 6 Implementation Plan: MCP client, then server (v1.0, part 1)

> Checkbox tasks, failing-test-first, one PR per task, a live gate run at the
> end. Style follows the Phase 3 to 5 plans.

**Goal:** Sable can use the MCP ecosystem, and the MCP ecosystem can use Sable
through its safety layer instead of raw SSH.

**Deliverables:** D1, D3, D4, then D2.

**Gate (from `docs/roadmap-phases.md` Phase 6, adjusted for the decisions below):**

```
/mcp add fs npx -y @modelcontextprotocol/server-filesystem /app   -> its tools listed
"use the filesystem tool to count markdown files in /app/docs"       -> a tool block mcp.fs.*, previewed, confirmed, result shown
/mcp trust fs.list_directory -> the next call runs without a confirm; /mcp list shows the tier
A server tool that asks for input (MRTR input_required) -> an in-shell prompt; the answer goes back once
/mcp search filesystem -> registry results with the add command
An MCP client drives `sable --mcp-serve` (stdio): run_command "ls" -> runs, audited;
  run_command "rm -rf /tmp/x" -> queued to /inbox, not run; the audit row names the MCP client
Node missing -> /mcp add of an npx server says so and how to install it; http servers still work
```

---

## 0. Decisions (asked and answered 2026-09-28)

| Question | Decision |
|---|---|
| Order | **Client first**, server after, as the roadmap orders it. |
| stdio servers and Node | **Support stdio and HTTP.** Node is not required; `/mcp add` of an `npx`/`node` command warns when `npx` is not on `PATH` and says how to install it. |
| Server mode transport | **stdio only for v1.0.** `sable --mcp-serve` speaks JSON-RPC on stdin/stdout; nothing listens on the network. HTTP with a token can come later. |
| Default tier for MCP tools | **`confirm`.** `/mcp trust <server>.<tool>` lowers one tool to `allow`; policy rules can still raise it. |
| New dependencies | **None.** JSON-RPC over `httpx` and `httpx-sse` (already approved) and `subprocess` for stdio. |

### 0.1 MCP tools are ordinary Sable tools

The roadmap sketched a new `action: "mcp"`. Instead, each discovered MCP tool
is registered in `sable/tools/registry.py` as a `Tool` named
`mcp.<server>.<tool>`, and the model calls it with the existing
`action: "tool"`. That path already previews every call, runs the policy gate
with the tool's tier as a floor, audits, publishes the bus event, counts
against the breaker budget and handles taint. A second action type would
duplicate all of it. MCP output is always untrusted: every result sets
`taints=True`, so the rest of the goal runs one tier stricter.

### 0.2 Spec versions

The target is spec 2026-07-28: stateless, `server/discover`, version and
capabilities in `_meta` on every request, MRTR (`resultType:
"input_required"` with `inputRequests`, retried with `inputResponses`).
Most published servers still speak 2025-06-18 with an `initialize`
handshake. The client tries `server/discover` first and falls back to
`initialize` + `notifications/initialized` when the server answers
"method not found". Task 0 reads the spec pages linked in
`docs/vision.md` before writing the framing, and the tests pin both paths.

### 0.3 Where it lives

`sable/mcp/` (`client.py`, `transports.py`, `servers.py`, `serve.py`), between
`agents` and `ui` in the layering rule, as `structure.md` places it. Server
definitions live in `config.json` under `mcp` (no secrets there); header
values and env vars may use `$SECRET:name`, resolved from the keyring as
`/secret` does.

### 0.4 Not in scope

MCP Apps, `subscriptions/listen`, the Tasks extension on the client side
(server-mode `spawn_task` returns a task name to poll with `list_tasks`),
sampling and roots (deprecated in the spec), HTTP server mode, OTel in
`_meta`.

## Task 0: MCP client core (D1, serial, first)

Files: `sable/mcp/transports.py`, `sable/mcp/client.py`,
`tests/fixtures/mock_mcp_server.py`.

- [ ] Failing tests against a fake stdio server (a small Python script in
      `tests/fixtures/`) and an `httpx.MockTransport` HTTP server: discover
      on a new-spec server, `initialize` fallback on an old one, `tools/list`
      with pagination, `tools/call` returning text content, a JSON-RPC error,
      a server that dies mid-call, a 30 s timeout.
- [ ] Stdio transport: `subprocess.Popen` (not a pty: this is a protocol pipe,
      not a user command), newline-delimited JSON, stderr drained to a log,
      process killed on close.
- [ ] Streamable HTTP transport: `httpx` POST, `timeout=httpx.Timeout(30.0)`,
      a JSON body or an SSE stream (`httpx-sse`) as the answer.
- [ ] `Client.discover()`, `list_tools()`, `call_tool(name, args,
      on_input=None)`. MRTR: an `input_required` result calls `on_input`
      with the requests and retries once with the answers; with no
      `on_input` the call fails with a clear message.
- [ ] Content: text parts joined; images and resources summarised as
      `[image, 12 KB]`; the result is capped at 64 KB.

## Task 1: `/mcp` and registering tools (D1, D4)

Files: `sable/mcp/servers.py`, `sable/app/builtins/mcp.py`,
`sable/tools/registry.py` (registration hook only).

- [ ] `/mcp add <name> <command...>` or `/mcp add <name> <https-url>`:
      connect, list tools, show them, store the server. Warn when the command
      needs `npx`/`node` and `shutil.which` cannot find it.
- [ ] `/mcp list` (servers, tools, each tool's tier), `/mcp remove <name>`,
      `/mcp trust <server>.<tool>`, `/mcp untrust ...`.
- [ ] At REPL start (lazily, on the first goal that needs tools, so cold start
      stays under 300 ms) connect the configured servers and register
      `mcp.<server>.<tool>` tools: tier `confirm` unless trusted, `taints` on
      every result, JSON Schema properties mapped to the registry's simple
      types (anything nested is passed through as `object`/`array`).
- [ ] A server that fails to start is reported once and skipped; the shell
      still works.

## Task 2: Elicitation in the shell (D1, MRTR)

Files: `sable/mcp/elicit.py`, the orchestrator's tool path.

- [ ] `on_input` for the interactive shell: each input request shown as a
      prompt with the server name and the question; strings, numbers,
      booleans and enums from the request schema; `q` declines.
- [ ] Workers and the daemon have no human: `on_input` is absent, the call
      fails with "needs input; run it from the shell".
- [ ] Answers are audited (redacted with the secret scanner), never logged raw.

## Task 3: `/mcp search` (D3)

Files: `sable/mcp/registry_search.py`, `sable/app/builtins/mcp.py`
(one subcommand).

- [ ] `GET https://registry.modelcontextprotocol.io/v0/servers?search=<q>`
      (verify the path when building), show name, description, transport and
      the exact `/mcp add` line; `/mcp search <q> --add N` runs it after a
      confirm.
- [ ] Offline or rate-limited: one clear line, no traceback.

## Task 4: `sable --mcp-serve` (D2, stdio)

Files: `sable/mcp/serve.py`, `sable/app/main.py` (flag only).

- [ ] Answers `server/discover` and, for old clients, `initialize`.
- [ ] Tools: `run_command` (policy: `allow` runs through the executor and is
      audited with agent `mcp:<clientInfo.name>`; `confirm` is queued to
      `policy_queue` and returns "queued as a7, approve with /inbox"; `deny`
      is refused), `list_tasks`, `spawn_task` (needs tmux; says so if absent),
      `get_skill`, `search_memory`.
- [ ] Every call audited with the client's name; nothing reads stdin except
      the protocol.
- [ ] Tests drive it over pipes with the Task 0 client.
