# Changelog

All notable changes are recorded here. Format follows [Keep a Changelog](https://keepachangelog.com/); versions follow SemVer once 1.0 ships.

## [Unreleased]

### Added
- **Phase 2 (B5): a validator that could not run is no signal.** Exit codes saying the *validator* failed to execute (curl's 7, connection refused; the shell's 127, command not found) now fall back to the run's own outcome instead of grading the skill a failure. 5 tests.
- Found by the Phase 2 gate run. `gpt-4o-mini` crystallised a deploy skill and chose `curl -sf localhost:8080/health` as its validator, a reasonable inference from the commands it was shown. Run anywhere the API is not up, curl exits 7 and the skill was graded a failure: confidence fell 0.50 to 0.40 to 0.35 across runs that had actually succeeded. That is the number measuring environment fit rather than skill quality, and it compounds, since each use costs 0.10 and a good skill used a few times on a machine where the service is not running drops out of retrieval entirely.
- A health check that genuinely fails returns 1 or 22, and those keep grading as failure, or the distinction becomes a way to never fail at all. The code set is deliberately short and curl-flavoured, because that is what models reach for, and is commented as the heuristic it is: knowing what a validator *is* belongs to B4's skill doctor. The reason string distinguishes the two cases, since "could not run" tells a user to check their environment and "exited 1" tells them to check the skill.
- Verified against the scenario that exposed it: with the unreachable validator still attached, the sequence now reads 0.50, 0.55, 0.60, 0.50, which is the gate's own numbers.
- **Phase 2 (B1): the orchestrator uses skills too.** Phase 2 shipped the skills loop into `agents/worker.py` only, which is the *spawned sub-agent*. The orchestrator is what a typed goal actually reaches, so an approved skill was used by the rarer path and ignored by the main one, and the phase's own goal statement ("the shell gets measurably better at a task the second and third time you do it") was untrue where a user would notice. The orchestrator now retrieves, injects, announces and grades. 17 tests.
- Retrieved **once, at construction**, not once per turn. The worker re-injects each step and leans on `TaskMemory`'s content-hash dedup; this class has no such memory and a 20-turn limit, so re-injecting would spend the context the work needs. The goal does not change mid-run, so one retrieval is also the correct one.
- Injected **after** the K11 project block and before history, so the model reads the repo's conventions first and the procedure second, and neither displaces the goal. The framing says the skill informs how the work is done while the goal still decides what is done.
- **An edited run grades nothing.** Every orchestrator command is human-confirmed and `e` lets the human rewrite it, so a run that needed editing is at best ambiguous evidence for the skill and at worst positive credit for a procedure that did not work. Withholding the nudge is the honest reading, and K3 already records what was edited. Grading also happens only on `done`: the other exits are a turn limit or an unreachable backend, neither of which says anything about the skill.
- Both collaborators are injected from `app/repl.py` with `None` defaults, the same inversion `corrections_db` and the worker's collaborators use, so no fourth `agents -> skills` edge appears and `test_layering.py` still XFAILs on its original reason.
- Verified against the live model: a typed goal retrieves the approved skill, prints `using skill deploy-api (0.55)`, puts the skill body in the prompt with the goal still ahead of it, moves 0.55 to 0.60 on a clean run, and holds at 0.60 when a command was edited.

### Fixed
- **Backends threw away any answer that was not the base schema.** `LLMResponse` carries eleven typed fields shaped around `{command, explanation, safe, plan}`, and every backend filled them with `parsed.get(...)` on exactly those names. A model answering a question *outside* that schema therefore had its whole answer discarded: the caller received a well-formed, wholly empty response, with no error and no way to tell "the model said nothing" from "the model said something we dropped". `LLMResponse` gains a `raw` field carrying exactly what the model said, set by all three backends. 7 tests.
- This was not hypothetical, and it made B3 **silently dead in production**. `gpt-4o-mini` answered the crystallisation prompt with correct JSON (`reusable`, `name`, `triggers`, `validate`, `body`), 166 completion tokens were billed, and `SkillCrystalliser.from_run()` drafted nothing at all. Found by the first live run of Task 13, not by any test: all 18 `from_run` unit tests passed throughout, because each stubbed a backend returning `explanation=<the JSON>` and so modelled the implementation rather than the transport.
- The new tests drive the **real backend objects against canned HTTP responses**, which is the seam every existing fixture skipped. A stubbed backend returning a hand-built `LLMResponse` cannot catch a bug in how a backend builds one. Writing them caught two more fixture errors of the same kind, an invented constructor argument and an SSE event shape guessed at rather than read from the parser.
- Additive, not a contract change: callers on the base schema keep reading the typed fields untouched, and a non-schema answer still reports no command rather than pretending one was returned. On OpenAI's re-ask path `raw` carries the retry text that actually parsed, not the first answer the model could not express as JSON.
- Verified against the live model: `from_run` now drafts a real `SKILL.md` with valid frontmatter and a validator the model chose, at `status = "pending"`, withheld from the loader until approved and retrieved after.
- **The sidebar lost its session panel.** Adding the corrections panel took the sidebar to seven panels, and since `_render_all` prints into a pane of fixed height with no notion of how much space is left, the first panel scrolled off the top: model, uptime, cwd and today's cost, gone. Nothing raised. It was caught only because an unrelated upgrade test greps a rendered tmux pane for the word "session". The corrections panel is now rendered only when it has something to report, which restores the default view.
- This is a stop-gap and is commented as one. It makes the overflow rarer without making it impossible: a user who is actively teaching the shell, which is exactly who K3 was built for, still gets seven panels. The real fix is `ui.sidebar.panels` from config plus a renderer that measures the space it has and says what it dropped (structure.md §3.3, Phase 4 G1/G6). Silent truncation is what made this invisible in the first place.
- Measuring it turned up something worse than the regression: in the playground container the sidebar overflows a 45 row pane by **seven** lines with only six panels, and did so before the corrections panel existed. The merge did not create the overflow, it pushed it far enough to eat the header.
- `tests/unit/test_sidebar_panels.py` pins the property that matters and holds everywhere, that the session panel survives a full render, plus an upper bound on height so the next panel trips a millisecond unit test instead of a two and a half minute integration run. The bound is set from the container, which renders six lines taller than the Windows host for the same tree; an exact height would pin whichever machine happened to run it.

### Changed
- **Phase 2 (Task 12): the misfiled integration placeholders now name the phase that owns them.** Fifteen `xfail(strict)` `NotImplementedError` placeholders were labelled "Phase 2", but none is a B or K deliverable: the full input loop belongs to Phase 4's blocks work (G2), backend SSE parsing to Phase 3.5's tool registry (J1), and session resume to Phase 7's Memory Palace (C6). The label was a generic future marker and claimed a debt against the wrong phase. `strict=True` and `raises=NotImplementedError` are unchanged, so an accidental implementation still fails the build.

### Added
- **Phase 2 (Task 7): crystallised skills are drafts pending approval, not auto-enabled.** This is the behaviour change the phase turns on, and the only task in it that alters something a user already relies on. `PatternWatcher` still runs at `/exit` and a pattern crossing the 3x threshold is still written to disk; what changed is that the skill lands `pending` and is inert until a human runs `/skill approve`. Before this, a cluster crossing the threshold started reaching a model's context with nobody having approved it, and the user was told "auto-generated" as their shell closed, with no way to act on the message and nothing saying it was now live. The gate's words are "never auto-enabled without approval", and this path was the one that broke them. 11 tests.
- The message now says "draft saved" and names the commands that review and enable it, because a notification with no next step is noise. The count is reported again at the **next login** by `pending_skills_banner()`, which is where a user can actually act on it; a draft nobody is told about is the same as no draft. It is silent when there is nothing pending, so a fresh install is not greeted by a count of zero or by an error from an index that does not exist yet.
- Exiting still always works. Crystallisation runs on the way out and a failure in it must never trap someone in a shell they asked to leave, so the existing guard stays and a test pins that the exit marker is written *before* the skills work rather than after it.
- Verified against real files: the `/exit` draft lands `pending`, `TaskSkillLoader` returns nothing for it, the login banner reads `1 draft skill pending approval`, and the banner goes silent once the skill is approved.
- Known seam: `crystallise()` still writes the pre-B2 flat layout (`~/skills/instructions/<slug>.md`) while `from_run()` writes folders, so the two crystallisation paths currently produce different formats. Both are pending, which is what the gate requires, and converting the `/exit` path is deliberately left as its own change rather than folded into a behaviour change.
- **Phase 2 (Task 11, worker half): an agent says which skill it is using.** A worker that injects a skill now prints `using skill deploy-api (0.55)` and publishes a `skill_used` bus event carrying each skill and its confidence. This is the only place the confidence loop is visible while it is happening: without it a user watching a run cannot tell a skill was retrieved at all, and "the shell got better at this" stays an assertion in a changelog. The wording is fixed by the Phase 2 gate, so it is a contract rather than a preference. 9 tests.
- Confidence renders to two decimals, which is also what keeps the index's float drift (`0.6500000000000001` after repeated nudges) away from a human who would reasonably read it as a bug. A skill with no recorded confidence is named without a number rather than given an invented one: local task skills have no index entry, and reporting a score for one would misdescribe what the model was given.
- Announced only when something was actually injected. A skill already seen earlier in the same run is filtered out of the injected text, and claiming to use a skill the model was not given that turn would be a lie the replay log contradicts.
- `EventKind.SKILL_USED` joins the within-a-turn kinds, deliberately outside `TERMINAL` so a reader does not stop tailing an agent after an announcement. Per `contracts.md` §2.1 an older sidebar carries an unknown kind rather than rejecting it, so this needs no sidebar change to be safe.
- The orchestrator half of this is still outstanding: `agents/orchestrator.py` was being modified concurrently and will announce its skills in a follow-up.
- **Phase 2 (B2): `/skill show`, `approve`, `reject`, `disable` and `stats`.** Until these existed a pending draft could not be approved from the shell at all: the crystalliser wrote one and the only way to enable it was editing `skills_index.json` by hand. `/skill list` now marks drafts and shows confidence, because a gate nobody can see is a gate nobody will use. 31 tests.
- `list` reads both layouts. B2 moved skills into `~/skills/<slug>/SKILL.md` and the pre-B2 flat files stay for a release, so listing only one would hide half a library. A skill on disk but missing from the index is shown as `(not indexed)` rather than omitted: the file is what can be injected, and a silent omission looks exactly like the skill having been lost.
- Every state change goes through `SkillIndex`, never by writing the file from the builtin. The index already writes file and entry in the order that fails safe, and a second copy of that rule in a builtin is how the two drift apart. `reject` drops the index entry and keeps the file, and says where it was kept.
- Verified against a real crystallised draft end to end: it lists as `draft, pending approval`, `show` renders its frontmatter and body, `approve` reports the 0.50 it was drafted at rather than inflating it, `disable` is reversible, and after `reject` the file is still on disk.
- **Phase 2 (B3): a skill can be drafted from one completed run.** `SkillCrystalliser.from_run()` asks the summariser whether a finished goal was a reusable procedure, and drafts a pending skill when it says yes. Until now a skill could only come from `PatternWatcher` noticing the same commands three times across sessions, at `/exit`; this catches the case that misses, a multi-step goal that worked once and whose procedure is worth keeping before it is ever repeated. 18 tests.
- Only a successful run of at least three executed steps qualifies, and the gate is arithmetic checked **before** the model is asked, so a run that does not qualify costs nothing. Asking first and discarding the answer would spend a summariser call on every short or failed goal in the system. A failed run is excluded because it teaches a procedure that does not work.
- The draft lands `status = "pending"` and `source = "crystallised"`. This is the path that would otherwise enable a skill silently, moments after a goal finished while the user is still reading the output, which is precisely what the gate forbids. Verified end to end against real disk: a fresh draft is invisible to `TaskSkillLoader` until approved, then appears.
- A refusal is honoured and writes nothing, or the question is theatre. So is an unparseable answer: unlike `crystallise()`, which writes a placeholder carrying its failure because a pattern crossed a threshold and the evidence should not vanish, here the model was asked a yes/no question and did not answer it, so drafting nothing is the honest response. An existing skill of the same name is never overwritten, since a skill the user approved and possibly edited outranks a new draft and replacing it would discard their edits and reset an earned confidence.
- Uses the summariser role (A5): judging reusability is summarising, not reasoning. The new `sable/llm/prompts/crystallise_check.md` is editable markdown like the other prompts, and tells the model to prefer an empty validator to a guessed one, because a wrong validator marks working skills as broken.
- **Phase 2 (B1, B5): the confidence loop closes.** `sable/skills/validate.py` grades a skill's use, and `agents/worker.py` nudges every skill a run used, once, at its terminal state. Until this landed `SkillIndex.nudge()` had no caller in the product and confidence never moved outside its own unit tests; the Phase 2 gate's third run was unreachable. 25 tests.
- Graded once per run, not once per step. A worker re-injects the same skills on every turn, so recording per step would take a skill from 0.5 to 1.0 on a single goal and make the number meaningless. Verified against a real index: a skill injected on five steps of one run moves 0.50 to 0.55, not to 0.75.
- Every exit path grades, not only `done`. The step limit, an unreachable LLM and a broken loop all reach the same call with `succeeded` False. A nudge on success alone would let confidence drift up forever and look like evidence, since a failure could never be recorded.
- **B5 validators.** A skill may declare `validate` in its frontmatter: a command answering "did this actually work?" more honestly than the agent's own say-so. An agent reporting `done` is grading its own homework; the validator asks the system. Verified end to end: a passing validator rescues a run the agent called a failure, and a failing validator catches one the agent called a success, which is exactly the gate's "break the deploy on purpose" step.
- The validator runs inside the worker's sandbox. It is text off disk, and once B7 lands it is text a stranger wrote, so running it unwrapped would make `validate = "rm -rf ~"` a working exploit against anyone who approved a skill without reading its frontmatter. It also gets a 30s ceiling rather than the command timeout, since it inspects state that already exists rather than doing the work.
- `agents/runtime.run_command` returns output and never an exit code, so the grader appends a marker and parses it back. That was a decision taken here rather than one the plan settled: the alternative was a second pty runner, and one runner with one timeout policy is worth more than a tidier return type. A validator that produces no marker, or times out, grades as a failure: a check that did not finish has not demonstrated success, and guessing in its favour is how a broken skill keeps its confidence.
- Both new `agents` to `skills` calls are deferred imports behind a module-owned wrapper, because `agents` sits below `skills` in the layering rule and `tests/unit/test_layering.py` tolerates exactly three such edges under a strict xfail. A fourth would fail the build rather than quietly passing.
- **Phase 2 (K4): natural-language aliases, resolved before the router.** `/alias "restart the api" = docker compose restart api` stores a phrase and the command it stands for, and typing that phrase runs the command. The match happens in `app/repl.py` ahead of `classify()`, which is the only place it can be both instant and free: anywhere later and the line has already cost a classification or a model turn. Matching is normalised (lowercased, punctuation stripped, whitespace collapsed) then compared with `difflib.SequenceMatcher` at a 0.9 threshold, so "Restart the API!" resolves and "restart the database" (0.74) falls through to the router untouched. `difflib` is stdlib, so this adds no dependency. 26 tests.
- The threshold is high on purpose. Silently running the wrong command because a sentence looked a little like a stored phrase is much worse than making someone type the phrase again, so a near miss is a miss.
- **An alias is not a safety bypass.** Resolving one produces a command string and nothing else; it then goes down the ordinary bash path, where `policy/engine.py:is_destructive` gates it exactly as it would a typed command. An alias standing for `rm -rf /var/lib/data` still asks for a typed confirmation.
- **Promotion is offered, never taken.** An alias reaching 3 uses prompts the user to turn it into a skill, and records that it asked, so an offer someone ignored does not reappear on every later use. Nothing is crystallised automatically, for the same reason Task 7 made drafting pending: a skill is text a model reads and acts on, so a human says yes.
- **Phase 2 (K3): the shell records what you corrected.** An `e`-edit at the orchestrator's confirm prompt now stores the (proposed, corrected) pair in a new `skill_corrections` table, and an answer to the `[b/a]` routing prompt stores one too. `/corrections` lists and deletes them, and the sidebar shows the week's count. The `[b/a]` recorder keeps writing its existing TSV corpus row as well: that corpus is the older contract behind the router accuracy programme (I3) and the correction is an addition to it, not a replacement. Both of its callers are wired, the `[b/a]` answer and the Ctrl+B bypass. 27 tests.
- A correction carrying a secret is **withheld entirely rather than stored redacted**, which is a deliberate departure from the "redact on the way in" rule `agent_turns` follows, and the reason is whitespace. `strip_secrets` ends in `" ".join(tokens)`, so it normalises runs of spaces and tabs; for the prose in a replay log that costs nothing, but this table stores shell commands, where `awk -F'\t'` coming back with a literal space instead of a tab makes the row a lie. A corpus that silently rewrites its own commands is worth less than one that is honest about what it dropped, so rows that are kept are byte-exact and the rest are counted. `/corrections` reports them ("3 withheld this week"), because a user who corrected five commands and sees two listed should be able to find out where the others went.
- This does not make the table airtight, and the limit is pinned by a test rather than assumed away: every shipped secret pattern is assignment-shaped (`api_key=`, `Bearer `), and the entropy fallback needs a score above 4.5, so a long but repetitive bare token can still slip through both. Widening those patterns was left alone on purpose, since they gate every command in the shell and a hasty regex there is a worse bug than a missing corpus row.
- The orchestrator takes its corrections database as an injected collaborator defaulting to `None`, rather than importing `skills` directly. `agents` sits below `skills` in the layering rule, and a fourth `agents -> skills` edge would have flipped `test_layering.py`'s strict xfail into an xpass and failed the build.
- **Phase 2 (B1): the loader consults the index.** `TaskSkillLoader.load_relevant()` was a keyword-only stub whose docstring said so; global skills now come back through `SkillIndex.get_ranked()`, best first, and an unapproved draft does not come back at all. This is where Phase 2's ranking first affects what a model actually sees: before it, the confidence the index had tracked since Phase 3 was write-only. The returned dicts keep the `name`, `content`, `hash`, `source` shape `agents/worker.py` reads and de-duplicates on, and `content` is the body only, since frontmatter in an agent's context is tokens spent on bookkeeping. 21 tests.
- Resolution order is local, then global folder skills, then the pre-B2 flat files Task 2 leaves in place for a release. A task-local skill still overrides a global one by name, and has no index entry to be ranked by, because the index only knows `~/skills`. A folder skill shadows its own flat original, since after migration both exist and the folder is the live copy.
- The gate does not depend on the index. A skill file carries its own `status` and that is checked whether or not an index entry exists, so deleting `skills_index.json` cannot enable every pending draft at once. A missing or corrupt index degrades to keyword matching over the files rather than returning nothing, which would look exactly like "this shell has no skills".
- Fixed before merge, both found by running the real loader against real files rather than by a unit test. **Approval did not reach the file:** `approve()` wrote `enabled` to the index while the file still said `pending`, and since the loader checks both, an approved skill was unreachable forever. Status now writes through to the file first and the index second, so a crash between the two leaves a skill withheld rather than wrongly enabled; a missing, unparseable or legacy flat file is left alone and the index update still proceeds, because a stale entry that cannot be approved would have no way to be cleared. **Matching ignored the description:** the pre-B2 rule tested goal words against the file's first line, which back then was the description, but B2 moved it into frontmatter that `_read` strips, so on the no-index path any skill whose body did not happen to repeat its description was invisible. Matching now reads name, description and first body line.
- **Phase 2 (B1, B3): the approval gate and confidence-ranked retrieval.** `SkillIndex` entries carry a `status` of `pending`, `enabled` or `disabled`, and `get_ranked()` returns only enabled ones. That single filter is what makes Phase 2's gate real rather than advisory: the crystalliser may draft a skill unattended, but nothing reaches a model's context until a human approves it. `approve()`, `disable()`, `reject()` and `pending()` back Task 8's `/skill` subcommands; `reject()` drops the index entry and leaves the file on disk, because rejecting is not deleting and a user should still be able to read what was proposed.
- `add()` still defaults to `enabled`, since every caller that exists today writes a skill the user asked for. The crystalliser opts into `pending` deliberately rather than the default flipping underneath its callers a task early. An unknown status raises, so a typo cannot produce a skill that is silently never injected.
- An index entry written before Phase 2 has no `status` key, and a missing status reads as enabled rather than pending. Treating it as pending would silently stop injecting every skill a user already has, the same failure the flat-file migration was careful to avoid. Verified against a genuine pre-Phase-2 index file, which keeps ranking normally and is not rewritten on read.
- Ranking is now `confidence x recency x use_count x match` rather than a two-key sort on confidence then use_count. Every factor is floored above zero so a brand new approved skill, which has no uses and no `last_used`, can still be retrieved; if any factor zeroed the product, an approved draft could never be used and so could never earn its first success. Recency decays on a 30-day half-life, use_count has diminishing returns so a much-used skill cannot drown out a better match, and equal scores keep index order so the skill named in an announcement does not change between runs for no visible reason.
- `nudge(name, success)` is the name the feedback loop calls the existing deltas by: a thin alias over `record_use` rather than a second scoring path, so the bus event and the index can never disagree about what a run was worth. An unknown name is a no-op, because grading happens after a run finishes and `/skill reject` may have removed the entry in between.
- One existing assertion changed deliberately: `test_get_ranked_orders_by_confidence_then_use_count` pinned the old two-key sort, so it was rewritten to pin the property a caller depends on (the more confident skill comes first) rather than the formula bent to preserve it. The two other `get_ranked` tests were unaffected.
- **Phase 2 (B2): flat skill files migrate into folders.** `sable/skills/migrate.py` turns every pre-B2 `~/skills/instructions/<slug>.md` into `~/skills/<slug>/SKILL.md` with inferred frontmatter, and repoints the matching `SkillIndex` entry at the new path so index and disk cannot disagree once the originals are removed. Confidence, use_count and last_used are carried over: a migration is a move, not a reset of a score the skill earned. 26 tests.
- The originals are kept for one release, the precedent the `shell/` compat shim set. Inferring frontmatter is a guess (the description comes from the first heading, and there is no honest source for triggers or a validator), so if the guess is wrong the user still has the file they wrote. Migrated skills land `enabled`, never `pending`: Phase 2's approval gate is about skills the machine drafted, and applying it retroactively to work a human already had running would be indistinguishable from this migration having lost them.
- Idempotent, because it runs on first use and so in practice on every startup. A skill folder that already exists is left alone and reported as skipped, since the folder is the live copy and may have been hand-edited since. One unreadable or unwritable file is reported and the rest still migrate: a skill is not safety-critical, so unlike the policy loader this carries on rather than raising.
- Fixed before merge, found by running the migration against real flat files rather than by a unit test: a skill with no heading inferred an empty `description`, which `render_skill` emitted and `parse_skill` then rejected as missing. The skill survived migration and would have vanished on the next startup. A headingless file now takes its slug as the description, which is a poor description and an honest one, and five round-trip cases pin that anything written can be read back.
- **Phase 2 (B2): the `SKILL.md` format and its parser.** `sable/skills/model.py` defines the `Skill` dataclass and the contract a skill folder carries: `name`, `description`, `triggers`, `preconditions`, `validate`, plus the `status` Phase 2's approval gate reads and the `source` Phase 8's K8 trust floor will read. Four things parse this format (the crystalliser writes one, the loader injects one, `/skill approve` flips one field, B7 will import one written by a stranger), so it is a contract and this module is the only place that knows it. 27 tests.
- Frontmatter is TOML inside a `+++` fence, not YAML: CLAUDE.md's approved dependency list has no YAML parser and `tomllib` is stdlib from Python 3.11, the same reasoning `policy/defaults/policy.toml` carries. The fence is `+++` rather than `---` on purpose, so a reader never mistakes it for YAML frontmatter that happens to parse, which is how a format drifts into being half-YAML by accident.
- Pre-B2 flat files still parse. Every skill a user already has is a bare markdown file with no frontmatter, and those load as legacy skills with the description inferred from the first heading, the same inference `loader.py` already does. A legacy skill is `enabled`, never `pending`: silently sending every existing skill to pending would be indistinguishable from the migration having lost them.
- Unknown frontmatter keys survive a round trip in `extra`, because B7 imports skills written against a later contract and B8 adds per-model notes; a parser that dropped what it did not recognise would corrupt those files on the first `/skill edit`. A malformed skill raises a typed `SkillFormatError` naming the file rather than yielding a half-built `Skill` that would inject an empty body into a model's context, but unlike the policy file it does not stop the shell: one unreadable skill means doing that work by hand, not running unguarded.
- **Phase 1 (A7): steer a running agent.** `/task <name> guide <text>` (and `Ctrl+G`, which prefills it) sends a line to a worker's stdin through tmux. The worker already drained a stdin guidance queue at the top of each turn; nothing could reach it. Guidance lands on the agent's next turn rather than interrupting the command in flight, which is the right granularity: killing a half-finished command to deliver advice loses the work. Sent with tmux's literal flag so a semicolon or a quote in the text is not interpreted, refused for an agent that has completed or been lost, and published to the bus so `/task events` shows that a human stepped in.
- **Phase 1: `/task <name> events`** renders the agent's bus stream, the same rows the orchestrator drains and the sidebar reads. Where `replay` answers "what was it thinking", this answers "what happened, and when".
- **Phase 1 (K11): repo-aware context.** When the working directory is inside a git repository, `CLAUDE.md`, `AGENTS.md` and `.sable.toml` from the repo root are loaded into the orchestrator's context as project instructions. People already write these for coding agents, so this is compatibility with a convention rather than a new one. `sable/agents/context.py`, 30 tests.
- The content is wrapped in `<project-instructions untrusted="true">` with framing that says it carries no authority: it can inform how work is done, never grant permission or relax a confirmation. Anyone can put a `CLAUDE.md` in a repository, and cd-ing into it must not hand that file the orchestrator's privileges. Reading is bounded at 8KB per file and 16KB in total so a large repo cannot crowd out the conversation.
- **Phase 1 (I7): degraded modes are announced, not silent.** `sable/core/health.py` checks for missing tmux, an unavailable bwrap sandbox, an unwritable or locked database, a terminal under 80 columns, and a missing keyring; the orchestrator reports an unreachable LLM the same way. Each banner says what is reduced *and* what to do about it, because a report without an action is noise. 20 tests.
- **Phase 1 (A2): `sable/agents/runtime.py`, the machinery both agents share.** The orchestrator and the worker each carried their own pty command runner, their own asyncio wrapper around `backend.complete()`, and their own fence-stripping JSON parse. The copies had drifted: the worker escalated its timeout to 600s for image and package pulls and announced the kill, the orchestrator did neither; the worker raised `RuntimeError` on an LLM timeout, the orchestrator let `asyncio.TimeoutError` escape. There is now one of each, and a typed `LLMUnavailable` for the timeout. 41 tests.
- This is helpers rather than the single `Agent(role=...)` class roadmap §3.1 asks for, and the module docstring says why: read side by side the two are not 70% duplicated. ### Fixed
- **A model answering with two JSON objects in one turn lost the whole turn.** `gpt-4o-mini`, asked for a multi-step goal, emitted a `run` object and a `spawn` object back to back. That is valid JSON followed by more valid JSON, which `json.loads` rejects as `Extra data`, so the turn was discarded and the goal abandoned. One action per turn is the contract, so the first complete object is the answer and anything after it is the model getting ahead of itself: `parse_llm_json` and `runtime.parse_json_action` now fall back to `raw_decode`, which takes that first object and stops. Genuinely broken JSON, a bare list and a truncated object still fail as before, each with a test.
- The orchestrator's system prompt now asks for exactly one object per turn, so the parser fix treats the symptom while the prompt addresses the cause.
- **A parse failure was reported as "LLM unreachable".** That label sent a real user to check a backend that was answering perfectly, and cost a round of debugging in the wrong place. `core/health.py` grows `llm_unparseable`, which says the backend is fine and suggests a stronger model for the role; the orchestrator picks between the two by exception type rather than lumping them together.
- **Natural-language goals never recorded their cost.** Nothing on the orchestrator path wrote a `token_events` row, and that is the table the sidebar, `/stats`, `/history` and `app/budget.py` all read. So a goal that genuinely billed the user's key reported `Cost $0.0000 · Calls 0`, and worse, the daily and session budgets could never trip on orchestrator spend because the rows they count did not exist. The token counts were already in `agent_turns`; they simply never reached the table everything else reads. `_record_cost` now writes one row per turn, tagged `nl_route` and attributed to the session. Found by running a real goal against a real key rather than by any test, which is why 12 now cover it.
- `_record_cost` creates `token_events` if it is missing, the same guard `EventBus` and `ReplayLog` already carry. An orchestrator can run in a process that never constructed `Database`, and a missing table would otherwise be swallowed as a silent zero, which is the exact failure being fixed.
- **The orchestrator described delegating instead of delegating.** Asked for a multi-step goal, `gpt-4o-mini` answered `{"action": "done", "explanation": "...so I'm delegating the task to a sub-agent"}`: it narrated the spawn in the one field that invites prose, and `done` ended the run. No sub-agent, no task row, no tmux window. The prompt listed `spawn` in its schema but never said that `done` terminates, so the model had no reason to think the two were exclusive. `sable/llm/prompts/orchestrator.md` now says so explicitly, and two tests pin the wording so the rule cannot be dropped silently. Diagnosed entirely from `agent_turns`, which is what the Phase 1 replay log was built for.
- `pricing.json` gains `gpt-4.1`, `gpt-4.1-mini`, `gpt-4.1-nano` and `o3-mini`. Only `gpt-4o` and `gpt-4o-mini` were priced, so every other OpenAI model computed to exactly $0.00 and reported it as fact.
- `/skill edit <name>` raised `NameError` on every invocation: the handler read `os.environ` and the module never imported `os`. Nothing caught it because `/skill` had no tests at all, which is the more interesting half of the bug; `tests/unit/test_skill_builtin.py` now covers list, new and edit.
- The spinner verb count was 186 everywhere; it is 187. `docs/vision.md` §2.6's verification command grepped for single-quoted strings, which skipped `"Beboppin'"` because its apostrophe forces double quotes in source. The command now counts with Python.
- `pyproject.toml` ships the new data files. Without the `package-data` globs and an `__init__.py` in `policy/defaults/`, an installed copy would have had no policy file and refused to start.
- The playground image ran Python 3.10 while `pyproject.toml` requires >=3.11 and CI tests 3.11/3.12, so every local test ran against a Python the project does not claim to support and could diverge from CI in either direction. `docker/Dockerfile.playground` moves to `ubuntu:24.04` (Python 3.12). Suite is unchanged across the bump: 338 unit and 76 integration on both.
- `/task new` raised `NameError` instead of spawning. The Phase 0.5 split moved `_get_recent_turns` into `app/builtins/task.py` but left the `_active_turns` global it read behind in the REPL. The handler already received the turns list as an argument, so it now uses that; covered by `tests/unit/test_task_builtin.py`, whose three `/task new` tests all fail against the broken version.
- **The playground had no telemetry sidebar or tasks bar.** `docker/playground-entry.sh` launched a single bare tmux pane, while `install.sh` builds three on a real machine, so the Phase 0 gate item "sidebar visible" could not be met. It now creates the same layout: shell, a 48-column telemetry sidebar and a tasks bar. Panes are sized by a `client-attached` / `client-resized` hook, because tmux resizes the session to the attaching client and would otherwise squeeze splits made beforehand; the sidebar collapses under 120 columns and returns above it. The hook addresses panes by id, since tmux renumbers indices as panes are created.
- **The SSH bypass did not fire for `ssh host cmd`, `scp` or `rsync`.** sshd runs the login shell as `sable -c "<command>"` and leaves `SSH_ORIGINAL_COMMAND` unset; that variable is only populated behind `ForceCommand` or an `authorized_keys` `command=`. The guard checked the env var alone, so a non-interactive SSH command landed in the interactive REPL instead of bash. It now takes the command from `argv` when invoked as `-c`, falling back to the env var. Found by running the Phase 0 gate in the playground, covered by `tests/unit/test_ssh_bypass.py` (6 of its 8 tests fail against the old guard).

### Changed
- **Phase 1: `sable/` has zero bare exception handlers,** down from 72 at the start of the phase. Every `except Exception` and every bare `except:` now names what the code underneath can actually raise: `sqlite3.Error` on database reads, `OSError` plus `subprocess.SubprocessError` wherever a process is spawned, `json.JSONDecodeError` on config and payload parses, `termios.error` where a pty is put into raw mode, `ImportError` where an optional dependency is reached for. Each keeps a comment saying why swallowing is right *there*, since the answer differs per site. `structure.md` §4.7 bans the pattern because unexplained silence is the worst failure mode this category of tool has; the lint in CI can become blocking now.
- The sweep surfaced a real bug it was meant to surface. `tests/unit/test_skill_crystalliser.py` constructed an `LLMResponse` without its three required positional fields, raising `TypeError`; the crystalliser's old `except Exception` swallowed it, so the test passed by silently taking the generation-failed branch and asserting only on the prompt it had already captured. With the handler narrowed, the error is visible and the test is fixed.
- **Two layering violations introduced in PR4 are gone.** `core/events/replay.py` imported `policy` for `strip_secrets`, and `core/health.py` imported `agents` for the bwrap probe: both are `core` reaching upward, the worst direction in the rule, and the pre-existing xfail was masking them. `ReplayLog` now takes the redactor as an argument (`policy/engine.py` grows `redact_text`, and the agents that record turns supply it), and the bwrap probe moved into `core/health.py` with `Sandbox` calling it, so the sandbox and the degraded-mode banner cannot disagree about what is available.

Typing the tmux handlers against libtmux's own exception base meant importing `libtmux.exc`, and a large part of the test suite replaces `libtmux` in `sys.modules` with a `MagicMock`, where resolving a *submodule* of a mock raises `ModuleNotFoundError`. A tmux error deriving straight from `Exception` escapes to the caller, which is correct: it means the manager is broken, not that one spawn was refused.

Measured cross-process delivery is 0.11s against the old 3 second poll, and exactly-once delivery no longer depends on a destructive read.
